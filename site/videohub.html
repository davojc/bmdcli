1. Connecting

Every bmd videohub command needs an address to talk to. The easiest way to get one is to ask the network: 

bmd discover

This listens for Blackmagic devices announcing themselves via mDNS on the local network and prints what it finds: 

NAME                               TYPE      ADDRESS
Blackmagic Smart Videohub 40 x 40  videohub  192.168.4.100:9990

Finding nothing is not an error — see known limitations below for why discovery sometimes comes up empty. To save the address without typing it by hand, add --add and pick the device from a numbered list: 

bmd discover --add

This needs a real interactive terminal — it prints each recognized device, asks you to choose one, and writes its address (and port, if not the default 9990) into config. Piped or scripted input is refused rather than guessed at: 

error: --add needs an interactive terminal; run bmd config set <type>.host <address> instead

If you already know the address — or discovery can't reach the device — set it directly: 

bmd config set videohub.host 192.168.1.50

Configuration is layered: a .bmdconfig file in the current directory (or the nearest parent directory that has one) overrides the global config file, and a command's own --host flag overrides both. This lets you keep a personal default globally while a project directory pins a different hub, and lets any single command override either for one-off use. When you're not sure where a value is coming from: 

bmd config list --show-origin

Each line is prefixed with the file it was read from, so a surprising value is easy to trace. Every command that talks to a device also accepts its own --host, --port, and --timeout, which is convenient for one-off use against a hub you haven't configured at all.

2. Looking at the hub

Once an address is configured, start by looking at what's there. All four of these are read-only, and every number bmd shows you — inputs, outputs, routes — is 1-based, matching the numbering printed on the device's own front panel. There is no "input 0". 

bmd videohub info
Model:          Blackmagic Smart Videohub 40 x 40
Friendly name:  Videohub
Protocol:       2.8
Video inputs:   40
Video outputs:  40
bmd videohub input list
N   LABEL
1   FoH Sw PGM
2   FoH Sw Aux
3   FoH Sw MV
4   Stage:Back:A:Cam
…
bmd videohub output list
N   LABEL                   INPUT  INPUT LABEL              LOCK
1   Projector AR            1      FoH Sw PGM               unlocked
2   Projector AL            1      FoH Sw PGM               unlocked
3   Stage Screen            1      FoH Sw PGM               unlocked
4   FoH MV 1                3      FoH Sw MV                unlocked
…

output list shows the lock column too — unlocked, owned (locked by this session), or locked (locked by someone else). If you only care about routing, route list is the same information without the lock column: 

bmd videohub route list
OUT  OUTPUT LABEL            IN  INPUT LABEL
1    Projector AR            1   FoH Sw PGM
2    Projector AL            1   FoH Sw PGM
3    Stage Screen            1   FoH Sw PGM
4    FoH MV 1                3   FoH Sw MV
…

3. Changing routes

To send a different input to an output, name the output first, then the input:

bmd videohub route set <output> <input>

For example, bmd videohub route set 4 13 sends input 13 to output 4. Both numbers are 1-based and validated against the device's real input/output count before anything is sent — an out-of-range number is refused up front rather than left for the device to reject: 

error: output must be between 1 and 40

Renaming an input or output works the same way, with the new label as the last argument:

bmd videohub input rename <input> <label>
bmd videohub output rename <output> <label>

Labels can be anything except a newline — the device's own protocol is line-oriented, so a newline in a label would corrupt it, and bmd rejects one before it's ever sent.

Locking an output stops other controllers from routing it (or taking the lock from you) without --force: 

bmd videohub output lock <output>
bmd videohub output unlock <output>
bmd videohub output unlock <output> --force

Without --force, unlocking an output someone else locked is left to the device to accept or refuse — it may say no. A route change against a locked output is refused the same way; see troubleshooting for what that looks like.

4. Backups

Every command that changes the device — route set, the two rename commands, lock, unlock, and restore — snapshots the device's current labels and routing before touching anything, and prints where that snapshot went: 

output 4 (FoH MV 1): FoH Sw MV → Switcher PGM
Backup: ~/.local/state/bmd/backups/192-168-4-100_blackmagic-smart-videohub-40-x-40/20260829-143512.json

Backups live under bmd's state directory, one subfolder per device (named from its host and model), one timestamped JSON file per change: ~/.local/state/bmd/backups/… on Linux and macOS, %LOCALAPPDATA%\bmd\backups\… on Windows. Each file is verified by reading it straight back after writing — if a backup can't be written and verified, the mutation is aborted before it touches the device. A route change never runs unprotected.

Three config keys control the behavior, all under backup.:

bmd config set backup.auto false   # turn off automatic backups entirely
bmd config set backup.keep 20      # keep the last 20 backups per device (default 10)
bmd config set backup.dir /path    # write backups somewhere other than the default

Older backups beyond the keep count are pruned automatically after each successful write. If you want to skip the backup for one specific command — scripting a burst of changes you've already backed up around, say — pass --no-backup on that command instead of turning the setting off globally.

5. The event workflow

Backups protect single changes, but for a whole event — walk in with a known-good routing state, make changes during the show, put it back afterwards — export and restore are the pair to use.

Before the event, capture everything:

bmd videohub export before.json

This reads the device, writes the snapshot, then reads the device a second time to confirm nothing changed while exporting — if it did, it retries rather than hand you a snapshot that was never actually true at any single instant. Locks are deliberately not captured; export is about labels and routing.

Afterwards, preview what putting it back would do without touching anything:

bmd videohub restore before.json --dry-run

Then actually apply it:

bmd videohub restore before.json

Restore only changes what differs — if the device already matches the snapshot, it says so and does nothing: 

Already matches the snapshot; nothing to do.

A snapshot can only be restored to the device it came from — a mismatched input/output count or model name is refused before anything is sent. And restore is safe to re-run: if a connection drops or the device rejects a change partway through, bmd stops immediately, reports how many of the planned changes actually applied, and re-running recomputes the remaining differences from the device's current state rather than repeating what already landed.

6. Watching

A Videohub isn't only ever changed by bmd — other controllers (a hardware control panel, a vendor app, another script) can route or rename things at any time, and the front panel itself can change routes and locks. watch streams every change as it happens, no matter who made it: 

bmd videohub watch

Each line describes one change:

route 4: FoH Sw MV → Switcher PGM
output 7 label: '#7' → 'House Left'
output 12 lock: unlocked → owned

Watch has no timeout of its own — it runs until you stop it with Ctrl+C, or the connection drops.

7. Scripting and agents

Every command accepts --json, which is the reliable thing to parse instead of the human-readable tables and sentences shown throughout this guide. Two shapes exist:

  • Every command except watch emits one JSON document per invocation — an object or array on stdout, printed once, with a clear beginning and end.
  • watch --json emits JSON Lines instead: one JSON object per line, one per update, because a live stream has no end to wrap a single document around.

Exit codes are consistent across every command, which makes them safe to branch on in a script:

  • 0 — success.
  • 1 — a runtime failure: couldn't connect, timed out, the connection dropped, or the device rejected a command (a NAK).
  • 2 — a usage error: a bad argument, an out-of-range input/output number, an incompatible snapshot, or a config value that doesn't parse.

One thing to know when experimenting with watch --json from a shell: piping it into something that only reads the first line, like 

bmd videohub watch --json | head -1

leaves the bmd process itself still running and connected in the background — head exiting after one line doesn't signal it to stop. Press Ctrl+C, or in a real script read the stream properly and let cancellation come from your own code.

8. Known limitations

  • mDNS discovery does not cross subnets, and some older Videohubs predate mDNS support entirely. Replies can arrive from another subnet in some network setups, but the query that triggers them does not cross routers — if bmd discover comes up empty on a hub you know is there, use bmd config set videohub.host <address> instead.
  • Windows may prompt for firewall access the first time you run bmd discover, since it listens on the network for mDNS responses. Allow it, at least on private networks, or discovery will find nothing.
  • discover --add writes the device's current numeric address — if it's on DHCP and its lease changes, the saved address goes stale and you'll need to run discover --add again (or config set by hand). A static address or a DHCP reservation for the hub avoids this entirely.
  • bmd videohub watch --json | head -1 leaves the watch process running — see scripting and agents above. Press Ctrl+C to stop it.
  • Discovery has so far been verified on Windows only. The underlying mDNS client is cross-platform code, but Linux and macOS haven't yet been exercised against real hardware.
  • macOS binaries aren't notarized, so Gatekeeper blocks the first run with "cannot be opened because the developer cannot be verified." The Finder right-click → Open workaround doesn't apply to command-line binaries — see the Download section for the actual fix (xattr -d com.apple.quarantine bmd).

9. Troubleshooting

Exit 0
Success. In a script, anything else means look at stderr.
Exit 1
A runtime failure — see below for the common ones.
Exit 2
A usage error — a bad argument, out-of-range number, or a snapshot/config value that doesn't parse. The device was never touched.

error: no host configured for videohub (run: bmd config set videohub.host <addr>)

No address is known from --host, the local .bmdconfig, or the global config. Run discover or config set as described in Connecting, above.

A device rejection (NAK)

The device answered but refused the specific change — bmd reports it as error: device rejected <description>. The most common cause is a locked output: attempting route set against an output someone else has locked gets refused this way. Unlock it first (bmd videohub output unlock <output>, possibly with --force), or route a different output.

A timeout, or the connection dropping mid-command

For a single mutating command, nothing further is sent once this happens — the command simply fails with exit 1. For restore, which can apply several changes in one run, bmd stops at the first one that fails, reports how many of the planned changes actually landed, and re-running restore is safe: it recomputes the remaining differences from the device's current state rather than reapplying what already succeeded.

A locked output won't accept a route change

That's the lock working as intended — see the NAK entry above. output list shows you the current lock state of every output if you're not sure which ones are held.
